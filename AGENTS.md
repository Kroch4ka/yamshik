# AGENTS.md — Yamshik

## Обзор проекта

**Yamshik** — Ruby-гем для унифицированной работы со службами доставки РФ («active_shipping для России»): СДЭК, Boxberry, Почта России, 5Post, Яндекс Доставка и т.п.

**Текущее состояние: стадия дизайна.** В репозитории пока нет кода — только дизайн-документ. Нет gemspec, Gemfile, тестов, CI. Все архитектурные решения зафиксированы в `DESIGN.md` (черновик v0.1, рабочий документ — правится прямо в тексте).

Состав репозитория:

- `DESIGN.md` — основной и единственный источник истины по архитектуре. Перед любой работой с кодом читать его целиком.
- `CONTRIBUTING.md` — процесс разработки (пайплайн PR, нейминг, CI, Definition of Done).
- `AGENTS.md` — этот файл.

## Целевая архитектура (из DESIGN.md)

- **Ядро + плагины.** Гем-ядро `yamshik` не знает про конкретные службы. Плагины — отдельные гемы по одному на службу (`yamshik-cdek` первым). Плагин при `require "yamshik/cdek"` регистрирует себя через `Yamshik.register_adapter(:cdek, Yamshik::Cdek::Adapter)` и в gemspec зависит от `yamshik ~> X.Y`.
- **Публичный API ядра** (semver): контракт `Yamshik::Carrier` + доменные классы. Версии API курьерок инкапсулированы в плагинах (`Yamshik::Cdek::V2::Adapter`); ядро про версии API не знает.
- **HTTP**: Faraday. Ядро отдаёт плагинам сконфигурированный `Yamshik::HTTP::Client`: ретраи с backoff, свой circuit breaker (closed/open/half-open), таймауты, логгер, маппинг сетевых сбоев в исключения.
- **Без ActiveSupport** в ядре (работа вне Rails). Rails-интеграция — возможный `yamshik-rails` в будущем.
- **Без вебхуков и поллинга в ядре.** Асинхронность выражена состоянием сущности (`registration_state: :pending | :registered | :rejected`) + refresh-методы; блокирующих ожиданий нет.
- **Правило расширения ядра**: сущность/метод попадает в ядро, только когда нужна минимум двум адаптерам. До этого — конфиг адаптера, методы плагина или аварийный выход через типизированный `carrier_options:`.

## Результаты и ошибки (принятые решения)

- Бизнес-результаты — Result-объекты (`result.success?`, `result.value`, `result.error`).
- Исключения — только инфраструктурные: `Yamshik::Error`, `TimeoutError`, `ConnectionError`, `RateLimitedError` (с `retry_after`), `AuthenticationError`, `InvalidResponseError`.
- `Result.err` содержит `Yamshik::CarrierError` как данные (не exception): `code`, `carrier`, `message`, `details`, `raw`, `carrier_code`. Таксономия кодов: `:validation_failed`, `:duplicate`, `:not_found`, `:route_not_supported`, `:rejected`, `:other` — см. DESIGN.md §2.

## Идемпотентность

- `Parcel#reference` — обязательный атрибут, генерируется клиентом; якорь идемпотентности.
- Адаптер декларирует `creation_strategy`: `:idempotent` (ретраим POST смело), `:check_on_ambiguous` (после неоднозначного сбоя — поиск по `reference`, потом повтор), `:unsafe` (ретрай POST отключён).

## Доменная модель

Единицы жёстко: **вес в граммах (`weight_g`), габариты в см (`length_cm`), деньги — Integer в копейках** (value-объект `Money` без зависимости от гема money). Конвертация — забота адаптеров.

Сущности v0.1: `Parcel`, `Contact`, `Company`, `Point`, `Item`, `Place`, `PlaceItem`, `PlaceLabel`, `ParcelService`, `TrackingEvent`. Полные списки атрибутов — в DESIGN.md §6. Скоуп v0.1 — только создание отправления (+ refresh регистрации); `Rate` (расчёт тарифа), `PickupPoint` (список ПВЗ), `PickupRequest` (вызов курьера) отложены в v0.2, `Merchant` живёт в плагине до второго адаптера.

Канонические статусы трекинга: `unknown`, `created`, `in_transit`, `ready_for_pickup`, `delivered` (терминальный), `to_return`, `lost` (терминальный), `problem` (с `problem_kind`). Маппинг «код службы → канонический» — таблицей данных в адаптере; неизвестный код → `unknown` + хук `config.on_unknown_status`. Списки — в DESIGN.md §7.

## Сборка и тестирование

Команд пока нет — код не написан. Планируемая стратегия (DESIGN.md §1):

- Тесты на **RSpec**. VCR-кассеты хранятся в репозитории каждого плагина.
- Ядро поставляет контрактный RSpec-сьют (`it_behaves_like "a yamshik carrier"`), который запускает каждый плагин.
- В ядре — референс-адаптер `Yamshik::Adapters::Fake` (пример, основа контрактного сьюта, мок для пользователей гема).

Когда появится код, стандартные команды будут `bundle install`, `bundle exec rspec`, `bundle exec rubocop` — но это нужно подтвердить по фактическому Gemfile/Rakefile, не считать данностью.

## Соглашения и стиль

- Основной язык документации и дизайн-обсуждения — **русский**. README гема планируется на английском, статья на Хабр — на русском.
- Лицензия — MIT.

## Процесс разработки

Полное описание — в `CONTRIBUTING.md`, кратко:

- **План работы и критерии приёма — в GitHub Issues и Milestones** (`v0.1`, `v0.2` в репозитории Kroch4ka/yamshik). Перед началом задачи читать её issue (`gh issue view N`): там критерии приёма чеклистом. PR закрывает issue через `closes #N` в описании.
- Хостинг **GitHub**. Работа только через PR: ветка от `main` → сразу Draft PR → тесты обязательны в том же PR → ревью → **squash merge**. Прямые пуши в `main` запрещены.
- Ветки: `<type>/<kebab-case-описание>` (`feat/carrier-contract`, `fix/result-nil-error`; типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`).
- Заголовки PR — Conventional Commits со scope (`feat(core): ...`, `fix(http): ...`); при squash заголовок становится коммитом в `main`.
- CI (GitHub Actions, блокирует merge): `bundle exec rspec` на матрице Ruby 3.2/3.3/3.4, `bundle exec rubocop` отдельной джобой, `gem build`; для плагинов — обязателен контрактный сьют ядра.
- Стиль: RuboCop + `rubocop-rspec`; публичный API ядра документируется YARD.
- Definition of Done: CI зелёный, поведение покрыто тестами, DESIGN.md/AGENTS.md обновлены при смене решений, заголовок PR по конвенции.

## Что важно при работе агентом

1. `DESIGN.md` — единственный авторитетный источник решений; при расхождении с ним сначала свериться с ним и при необходимости обновить его.
2. Не добавлять в ядро сущности, нужные только одной службе (правило двух адаптеров).
3. Не вводить ActiveSupport, вебхуки, поллинг и блокирующие ожидания в ядро.
4. Соблюдать жёсткие единицы измерения (граммы, см, копейки) и разделение «исключения = инфраструктура, Result = бизнес».
5. `carrier_options` — аварийный выход, а не норма: добавлять только там, где реально требует API текущего плагина; валидация с указанием пути (`details.path`); ключ, нужный второму адаптеру, поднимается в атрибут сущности (DESIGN.md §5).
